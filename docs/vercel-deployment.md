# Vercel and Neon deployment

Phase 1 runs the Next.js application and the `capture-requests` queue consumer on Vercel. Neon
provides PostgreSQL. Hosted connectors and the legacy interval scheduler stay disabled.

## Runtime topology

| Component           | Region                                                     | Connection / trigger                             |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| Next.js application | Vercel `sin1`                                              | `DATABASE_URL` (pooled)                          |
| Capture worker      | Vercel `sin1`, maximum 60 seconds on Hobby Preview         | Vercel Queue topic `capture-requests`            |
| Research worker     | Vercel `sin1`, one stage per 60-second invocation          | Vercel Queue topic `research-runs`               |
| PostgreSQL          | Neon Singapore region, where the selected plan supports it | Pooled URL at runtime; unpooled URL for releases |

The PostgreSQL client uses at most four connections per function instance and sets
`prepare: false`, which makes it safe to use with Neon's transaction pooler. Do not point
`DATABASE_URL` at an unpooled endpoint: serverless instances scale independently and can exhaust
the database connection budget.

The queue route is registered in `vercel.json`. Queue messages contain only
`{ "version": 1, "captureId": "<uuid>" }`. Vercel acknowledges a message only after the durable
worker returns. A thrown transient processing error leaves the message available for redelivery.

Vercel supplies `VERCEL=1`, deployment metadata, and Queue credentials. Do not create a public
environment variable for a capture token, session secret, queue credential, database URL, or AI
provider key. `DISTIL_API_TOKEN` is optional legacy compatibility only and should not be used by
new clients.

Account export needs all three object-store variables in a hosted environment. With any of them
missing the worker marks the export `failed` (`EXPORT_STORAGE_UNAVAILABLE`) and the account page
shows that state; hosted deployments never fall back to local file storage. Changing them is an
environment change that needs Amit's authorization, followed by a redeploy.

For local development, use a local/test PostgreSQL URL and a local dispatcher. Hosted Preview and
Production must use Vercel Queue; they must not use timers, an in-memory dispatcher, the legacy
SQLite file, or database polling as a queue substitute.

## Preview release

1. Create a disposable Neon branch in the Singapore region where available.
2. Store its pooled URL as Preview `DATABASE_URL`.
3. Keep its unpooled URL in the release environment as `DATABASE_MIGRATION_URL`.
4. Apply every unapplied SQL migration through the ledger-aware release command:

   ```bash
   npm run db:migrate
   ```

   Do not apply migration files directly with `psql`: bypassing `distil_migrations` makes a later
   release attempt to replay already-created schema objects.

5. Run the importer without `--execute` and inspect its table counts and exclusions:

   ```bash
   npm run db:import:sqlite -- data/distil.db
   ```

6. Import only after the dry run is correct:

   ```bash
   npm run db:import:sqlite -- data/distil.db --execute
   ```

7. Deploy the exact reviewed commit to Vercel Preview.
8. Complete the smoke checklist below. Keep the Neon branch until review is complete.

Migrations never run during module import, `next build`, application startup, or a request. A
failed migration stops the release before traffic changes. The SQLite importer performs writes
only with `--execute`, uses the unpooled URL, verifies IDs and counts in one transaction, and does
not modify the source SQLite file.

## Production release

1. Confirm CI and the Preview smoke checklist pass for the exact commit being promoted.
2. Take and retain a Neon restore point according to the account's backup policy.
3. Retain the original SQLite database and the currently active Vercel deployment.
4. Run `npm run db:migrate` with production `DATABASE_MIGRATION_URL` as an explicit release step.
5. Run the SQLite importer in dry-run mode against the retained source and review counts.
6. Run the importer with `--execute`; retain its verification output in the release record.
7. Promote the verified commit to Production.
8. Connect the browser extension through its sign-in flow and pair the iPhone Shortcut from
   Settings → Capture → iPhone. Manual tokens remain for scripts and legacy clients; never reuse
   an administrative session as a capture credential.
9. Complete the smoke checklist against the production origin.

### Release pin

The build preflight (`src/lib/operations/phase3-auth-activation.ts`) reports a `sha-binding`
finding, and the build fails, unless `DISTIL_PHASE3_PRODUCTION_SHA` (Production) or
`DISTIL_PHASE3_REHEARSAL_SHA` (Preview) equals `VERCEL_GIT_COMMIT_SHA`. The variable also accepts
the literal value `unpinned`: the `sha-binding` finding is then skipped and every push to `main`
auto-deploys through Vercel's Git integration, while every other preflight finding (origin binding,
cookie secret length, role separation, allowed origins) still applies. The variable remains
required, so opting out is explicit and visible in the environment settings.

- **Iteration phase (current intent):** set `DISTIL_PHASE3_PRODUCTION_SHA=unpinned` on Production
  (optionally the rehearsal variable on Preview). Set it only after a build that understands the
  value has been deployed once under the existing exact pin; older builds treat `unpinned` as a
  mismatching SHA and fail.
- **Re-tighten:** set the variable back to the exact commit SHA you intend to deploy. From then on
  each release again requires updating the pin before the deploy.

Changing either variable is a Vercel environment mutation and needs Amit's task-specific
authorization (`AGENTS.md` section 9).

## Smoke checklist

- `GET /api/health` returns `200`, `cache-control: no-store`, and only
  `{ "status": "ok", "service": "distil" }`.
- An unauthenticated feed or settings request does not render private data.
- Login succeeds with the deployed password and fails with an incorrect password.
- A new capture returns `202` only after the capture receipt and queue publication are durable.
- The receipt progresses from `queued` through `processing` to `ready`.
- Repeating the same canonical URL returns `200` with the existing receipt/item.
- A controlled transient upstream failure can be retried and does not create a second item.
- Regenerating the manual capture token causes requests using an old manual token to return
  unauthorized while browser connections, phone pairings and session login remain valid.
- Settings → Capture shows the iPhone card without console errors. Disconnecting a phone makes
  its next capture return `401 UNAUTHORIZED`; other connections remain active.
- The queue consumer appears for topic `capture-requests`, has a 60-second Hobby Preview duration, and shows no
  continuously failing deliveries.
- The queue consumer for topic `research-runs` exists (created in the Vercel dashboard, Storage →
  Queues, before the first research run); a signed-in deep research run completes through its
  stages and `research_reports.progress` is cleared on completion.
- Application, queue, and test logs contain no plaintext capture tokens, database URLs, passwords,
  session secrets, OAuth credentials, or AI keys.
- Gmail, Slack, publisher synchronization, the local scheduler, and database polling are inactive.

## Rollback

Rollback changes the application deployment only:

1. Stop promotion and disable any newly issued test capture tokens.
2. Use Vercel's deployment history to promote the previously verified deployment.
3. Verify `/api/health`, login, and read access on that deployment.
4. Leave PostgreSQL migrations and imported rows in place. Phase 1 migrations and imports are
   additive and are not automatically reversed or deleted.
5. Preserve the failed deployment, queue delivery evidence, importer output, Neon restore point,
   and original SQLite files for diagnosis.

Do not run destructive down migrations, delete imported rows, or replace the source SQLite file as
part of application rollback. If database recovery is required, treat it as a separate incident
with an explicit restore plan.

## iPhone Shortcut install link

`NEXT_PUBLIC_IOS_SHORTCUT_URL` is the public iCloud link for the signed **Save to Distil** Shortcut.
Amit builds and signs the Shortcut on his iPhone, shares one link for all users, then sets the
variable in Vercel. It is optional: when unset, Settings → Capture → iPhone hides **Get the
Shortcut** while keeping pairing and connection management available. There is no installer URL
or signed Shortcut artifact supplied by this repository. Follow the
[iPhone recipe and device checklist](iphone-shortcut.md).

The `NEXT_PUBLIC_` value is included at build time; rebuild/redeploy after Amit sets or changes it.
Keep Preview unset unless the linked Shortcut targets the matching Preview origin and uses a
separate credential file. The public artifact contains API URLs and actions, never a user's code,
capture token or credential file. The Production artifact targets `https://distilai.app`.

Before releasing code that uses phone pairing, Amit runs the read-only Production pre-check,
applies `npm run db:tenant:migrate -- --stage phone-pairing` with the owner connection, and runs
the post-check. Stage `phone-pairing` (`0016_phone_pairing.sql`) requires the existing
`browser-connections` stage. The release owner merges only after the schema checks succeed and
Amit gives task-specific authorization; the merge can auto-deploy. Agents do not perform this
Neon mutation or the install-link environment change. Keep local verification, release smoke and
Amit's physical iPhone acceptance separate in the state log.

## Admin invitations (Settings → Invitations)

A user whose id is listed in `DISTIL_ADMIN_USER_IDS` sees Settings → Invitations and the
Troubleshooting tab. The routes under `/api/v1/admin/invitations` enforce the allowlist on the
server (403 for everyone else, including a capture token for an admin account). Because the runtime
database role cannot read or write `invitations`, the routes use the control-plane client, so
`DATABASE_CONTROL_PLANE_URL` must be set where the admin feature is used (the account-lifecycle
queue already needs it); without it they answer 503. Each issue and revoke also writes an
`operator_audit_events` row. Setting either variable in Vercel is an environment change that needs
Amit's authorization at release time. Locally, put your user id in `DISTIL_ADMIN_USER_IDS` and point
`DATABASE_CONTROL_PLANE_URL` at the same Docker owner URL as `DATABASE_MIGRATION_URL`.

## Docs-only commits do not build

`vercel.json` sets `ignoreCommand` to `scripts/vercel-ignore-build.sh`, Vercel's Ignored Build Step.
It compares `HEAD` with `VERCEL_GIT_PREVIOUS_SHA` (the last successful deployment of the branch)
and skips the build when every changed file is under `docs/`, is a Markdown file, or is under
`.github/`. Any other change, a missing previous SHA, or a previous SHA outside the shallow clone
builds as before. A redeploy of the same commit (to pick up a changed environment variable) always
builds. Vercel's exit-code convention is inverted: exit 0 skips, exit 1 builds. This
overrides the dashboard's Ignored Build Step setting, so change it here, not in the dashboard.
