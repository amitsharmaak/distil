# Vercel and Neon deployment

Phase 1 runs the Next.js application and the `capture-requests` queue consumer on Vercel. Neon
provides PostgreSQL. Hosted connectors and the legacy interval scheduler stay disabled.

## Runtime topology

| Component           | Region                                                     | Connection / trigger                             |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| Next.js application | Vercel `sin1`                                              | `DATABASE_URL` (pooled)                          |
| Capture worker      | Vercel `sin1`, maximum 300 seconds                         | Vercel Queue topic `capture-requests`            |
| PostgreSQL          | Neon Singapore region, where the selected plan supports it | Pooled URL at runtime; unpooled URL for releases |

The PostgreSQL client uses at most four connections per function instance and sets
`prepare: false`, which makes it safe to use with Neon's transaction pooler. Do not point
`DATABASE_URL` at an unpooled endpoint: serverless instances scale independently and can exhaust
the database connection budget.

The queue route is registered in `vercel.json`. Queue messages contain only
`{ "version": 1, "captureId": "<uuid>" }`. Vercel acknowledges a message only after the durable
worker returns. A thrown transient processing error leaves the message available for redelivery.

## Environment mapping

Use separate Neon databases or branches for Preview and Production. Never give a preview
deployment the production URL.

| Variable                          | Preview                     | Production                    | Notes                                                         |
| --------------------------------- | --------------------------- | ----------------------------- | ------------------------------------------------------------- |
| `DATABASE_URL`                    | Preview branch pooled URL   | Production pooled URL         | Runtime requests and queue worker                             |
| `DATABASE_MIGRATION_URL`          | Preview branch unpooled URL | Production unpooled URL       | Release/import process only; do not make it a client variable |
| `DISTIL_SESSION_SECRET`           | Independent preview secret  | Independent production secret | At least 32 random bytes                                      |
| `DISTIL_WEB_PASSWORD_HASH`        | Preview password hash       | Production password hash      | Scrypt value generated by the application utility             |
| `DISTIL_ALLOWED_ORIGINS`          | Exact preview origin(s)     | Exact production origin(s)    | Comma-separated HTTPS origins; no wildcard                    |
| `FEATURE_CONNECTORS`              | `false`                     | `false`                       | Gmail, Slack, and publisher connectors remain out of scope    |
| `SYNC_INTERVAL_HOURS`             | `0`                         | `0`                           | Defense in depth while hosted scheduler startup is disabled   |
| `NEXT_PUBLIC_SYNC_INTERVAL_HOURS` | `0`                         | `0`                           | Keeps connector schedule claims out of the hosted UI          |
| AI provider secret(s)             | Preview-scoped              | Production-scoped             | Configure only the provider selected for the deployment       |

Vercel supplies `VERCEL=1`, deployment metadata, and Queue credentials. Do not create a public
environment variable for a capture token, session secret, queue credential, database URL, or AI
provider key. `DISTIL_API_TOKEN` is optional legacy compatibility only and should not be used by
new clients.

For local development, use a local/test PostgreSQL URL and a local dispatcher. Hosted Preview and
Production must use Vercel Queue; they must not use timers, an in-memory dispatcher, the legacy
SQLite file, or database polling as a queue substitute.

## Preview release

1. Create a disposable Neon branch in the Singapore region where available.
2. Store its pooled URL as Preview `DATABASE_URL`.
3. Keep its unpooled URL in the release environment as `DATABASE_MIGRATION_URL`.
4. Apply every unapplied SQL migration through the ledger-aware release command:

   ```bash
   npm run db:migrate
   ```

   Do not apply migration files directly with `psql`: bypassing `distil_migrations` makes a later
   release attempt to replay already-created schema objects.

5. Run the importer without `--execute` and inspect its table counts and exclusions:

   ```bash
   npm run db:import:sqlite -- data/distil.db
   ```

6. Import only after the dry run is correct:

   ```bash
   npm run db:import:sqlite -- data/distil.db --execute
   ```

7. Deploy the exact reviewed commit to Vercel Preview.
8. Complete the smoke checklist below. Keep the Neon branch until review is complete.

Migrations never run during module import, `next build`, application startup, or a request. A
failed migration stops the release before traffic changes. The SQLite importer performs writes
only with `--execute`, uses the unpooled URL, verifies IDs and counts in one transaction, and does
not modify the source SQLite file.

## Production release

1. Confirm CI and the Preview smoke checklist pass for the exact commit being promoted.
2. Take and retain a Neon restore point according to the account's backup policy.
3. Retain the original SQLite database and the currently active Vercel deployment.
4. Run `npm run db:migrate` with production `DATABASE_MIGRATION_URL` as an explicit release step.
5. Run the SQLite importer in dry-run mode against the retained source and review counts.
6. Run the importer with `--execute`; retain its verification output in the release record.
7. Promote the verified commit to Production.
8. Create separate capture tokens for the iPhone Shortcut and browser extension. Do not reuse an
   administrative session or share one capture token across clients.
9. Complete the smoke checklist against the production origin.

## Smoke checklist

- `GET /api/health` returns `200`, `cache-control: no-store`, and only
  `{ "status": "ok", "service": "distil" }`.
- An unauthenticated feed or settings request does not render private data.
- Login succeeds with the deployed password and fails with an incorrect password.
- A new capture returns `202` only after the capture receipt and queue publication are durable.
- The receipt progresses from `queued` through `processing` to `ready`.
- Repeating the same canonical URL returns `200` with the existing receipt/item.
- A controlled transient upstream failure can be retried and does not create a second item.
- Revoking a dedicated test token causes subsequent Shortcut/extension requests to return
  unauthorized while existing session login remains valid.
- The queue consumer appears for topic `capture-requests`, has a 300-second duration, and shows no
  continuously failing deliveries.
- Application, queue, and test logs contain no plaintext capture tokens, database URLs, passwords,
  session secrets, OAuth credentials, or AI keys.
- Gmail, Slack, publisher synchronization, the local scheduler, and database polling are inactive.

## Rollback

Rollback changes the application deployment only:

1. Stop promotion and disable any newly issued test capture tokens.
2. Use Vercel's deployment history to promote the previously verified deployment.
3. Verify `/api/health`, login, and read access on that deployment.
4. Leave PostgreSQL migrations and imported rows in place. Phase 1 migrations and imports are
   additive and are not automatically reversed or deleted.
5. Preserve the failed deployment, queue delivery evidence, importer output, Neon restore point,
   and original SQLite files for diagnosis.

Do not run destructive down migrations, delete imported rows, or replace the source SQLite file as
part of application rollback. If database recovery is required, treat it as a separate incident
with an explicit restore plan.
